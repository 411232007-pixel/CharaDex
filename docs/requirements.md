次元圖鑑 CharaDex：需求文件
版本：初步規劃 v0.1
狀態：本文件描述預期需求，不代表功能已完成。
1. 專案目的
建立一支在個人電腦上執行的 Discord Agent。使用者在指定頻道上傳動漫或遊戲角色圖片後，系統辨識角色、搜尋及核對資料，並回傳繁體中文角色資料卡與資料來源，減少使用者自行查找多個網站的時間。
2. 使用者與操作情境
- 對象：想認識動漫、漫畫或遊戲角色的使用者。
- 主要輸入：一張含有一位主要二次元角色的圖片。
- 主要輸出：角色辨識結果、角色資料卡、辨識依據及可點擊的來源連結。
- 僅處理設定的 Discord 頻道，忽略其他 Bot 與自己的訊息。
- 同一頻道可供不同使用者操作，各人的查詢紀錄與收藏分開保存。
3. 核心處理流程
1. 接收圖片，檢查檔案格式、大小及實際內容，並回覆處理中狀態。
2. 分析角色外觀，例如髮型、服裝、武器、配件與標誌，產生候選角色。
3. 使用實際可用的搜尋或資料查詢工具核對候選與角色資料。
4. 辨識充分時回傳資料卡；不確定時列出至多三位候選與理由，請使用者確認。
5. 保存查詢結果與來源，供後續查閱、收藏和比較。
6. 完成或失敗後清除暫存圖片；錯誤時提供清楚且可採取行動的訊息。
第一版以單張圖片、單一主要角色為範圍。多人圖片請使用者指定位置或裁切後重傳；資訊不足或原創角色無法確認時，允許回覆無法辨識。
4. 角色資料卡欄位
欄位	需求
名字	中文名稱；有可靠依據才補充原文名稱、英文名稱或別名
作品出處	動畫、漫畫或遊戲名稱，必要時註明版本或時間線
年齡	依來源記載；官方未公開則明確標示，不依外貌推算
身分／職業	主要身分、職業，必要時補充組織或陣營
個性與核心動機	提供簡短摘要，區分官方設定與劇情歸納；無依據則標示未知
能力／武器	主要能力、代表性武器或裝備，無則註明
聲優	標示配音語言及聲優；作品或版本不同時分開列出
辨識依據與狀態	說明外觀線索，標示較有把握、待確認或無法辨識，不編造精確機率
資料來源	實際查閱的頁面標題與網址，註明所支持的資料及查詢時間


預設避免重大劇透。涉及重大劇情的核心動機先提供不劇透摘要，經使用者要求才展開。
5. 資料可信度與例外處理
- 優先使用官方角色介紹、官方網站或公告；不足時可使用可信資料庫或維基，並標示非官方來源。
- 模型辨識與記憶只能作為候選或待查證線索，不等於已核實資料。
- 搜尋失敗時明確標示「尚未完成網路查證」，不得假造網址、聲優、年齡或其他資訊。
- 無資料、官方未公開及來源互相矛盾應分別說明。
- 不同版本、不同時期或同名角色不可任意合併。
- 同人圖與換裝圖應綜合多項特徵判定，不能只依髮色猜測。
- 未確認的候選不加入正式收藏或收藏統計。
- 不支援辨識真人身分；非支援內容應回覆使用範圍。
6. 功能與指令
下列為建議文字指令，實作時應維持一致並提供說明。
功能	操作	預期結果
圖片辨識	上傳圖片	回傳資料卡，或候選確認提示
使用說明	!說明	顯示支援輸入、指令及限制
文字查詢	!查角色 名稱	搜尋並回傳資料卡，同名時先選作品
歷史查詢	!最近	顯示自己的最近十筆已完成查詢及紀錄 ID
查看舊結果	!角色 紀錄ID	讀取自己的已保存資料卡，標示原查詢時間
收藏角色	!收藏 紀錄ID	收藏自己紀錄中的已確認角色，重複收藏不重複計數
查看收藏	!收藏列表	顯示自己的角色收藏
統計	!統計	計算個人完成查詢次數、收藏角色數、各作品收藏數及占比
比較	!比較 紀錄ID1 紀錄ID2	讀取自己的兩筆舊結果，比較作品、身分、個性及能力，不捏造戰力排名
刪除紀錄	!刪除紀錄 紀錄ID	刪除自己的指定查詢；若收藏依附此紀錄，清楚說明並一併處理


統計定義：
- 查詢總次數：已完成並保存結果的查詢數；失敗或等待確認不計入。
- 收藏角色數：以作品和角色身分識別後的不重複角色數；同一角色不同圖片不重複計算。
- 各作品占比：該作品收藏角色數 ÷ 個人收藏角色總數 × 100%，顯示至小數點一位；四捨五入後總和可能略有差異。
- 第一版每個收藏角色歸屬一個主要作品分類，避免跨作品重複計數；有歧義應先確認。
- 無收藏時顯示尚無收藏，不執行除以零。
- 數量與占比必須由程式根據保存資料計算，不交由語言模型猜測。
7. 儲存與使用者區分
- 每筆查詢需有唯一紀錄 ID、Discord user ID、時間、角色識別資訊、資料卡內容、來源及查證狀態。
- 以 Discord user ID 區分各人的查詢與收藏，不使用可能變動或重複的暱稱作為唯一識別。
- 所有歷史、收藏、比較及刪除操作都必須驗證資料擁有者。
- 重新啟動程式後仍可查閱已保存紀錄。
- 原始圖片預設不永久保存。
- 資料按帳號隔離不代表回覆保密：在公共頻道的回覆仍可被頻道成員看到，使用說明需寫清楚。
8. 執行環境與安全限制
- 在 Windows PowerShell 環境操作，優先採 Python 3.12 與 uv 管理套件，Discord 使用 Gateway Bot 模式。
- Discord Token、指定頻道 ID 及必要服務設定放在本機環境設定；提供不含真實機密的 .env.example。
- 第一次提交前設定 .gitignore，排除 .env、憑證、使用者資料庫、日誌、暫存圖片與虛擬環境。
- 對圖片大小、格式、解碼後尺寸、每人請求頻率、並行數量及處理逾時設定合理上限，於架構文件記錄數值。
- 限制下載來源，不允許使用者藉圖片網址存取任意內部網路或本機檔案。
- 圖片、使用者文字、網頁文字均視為不可信資料，不可覆蓋系統指令。
- 如使用 claude -p，單筆工作在隔離暫存資料夾執行，限制工具與權限，不能讀取專案機密或任意執行命令。
- 檢查模型輸出結構與長度，清洗檔名，資料庫使用參數化查詢，避免非預期 mention。
- Discord 回覆過長時分段或使用 Embed，保留完整來源連結。
- 錯誤回覆不得洩漏 Token 或內部機密；必要日誌不得記錄金鑰。
- 不預設已有額外付費 API。圖片理解與搜尋各使用何種工具、權限及費用，須在架構規劃時確認；不得自行購買服務。
9. 開發範圍與階段
1. 核心版：圖片接收、角色候選、實際搜尋查證、資料卡、不確定與失敗處理。
2. 延伸版：依人保存的歷史紀錄、文字查詢、收藏、統計、比較與刪除。
3. 驗收版：錯誤與安全檢查、文件及真實 Discord 展示。
第一版不要求網站介面、模型訓練、涵蓋所有作品的自建角色資料庫、多人圖片自動分割或主動定時通知。
10. 驗收條件
- 上傳一張可辨識的角色圖，能取得上述欄位的資料卡及實際來源；沒有依據的欄位明確標示未知。
- 不確定圖片能進入候選確認流程，不硬猜。
- 多人圖、非圖片、過大檔案、搜尋失敗與逾時都有明確回覆。
- 能讀取先前保存的兩筆紀錄並比較；重新啟動後紀錄仍存在。
- 兩個 Discord 帳號使用相同指令，取得各自資料，不能讀取或刪除對方紀錄。
- 重複收藏不增加角色數，作品數量與占比計算正確，無收藏時可正常回覆。
- 公開 repository 與歷史 commit 不包含 Token 或其他金鑰。
- README 的已完成功能與實際程式及展示行為一致，待完成與未驗證項目分開列出。
